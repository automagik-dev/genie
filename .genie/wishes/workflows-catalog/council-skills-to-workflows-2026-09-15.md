## Synthesizer reading and consensus

My own reading first: the strongest thing in these five responses is not the ranking, it is the correction to the premise. The decision was framed as token optimization, and four of five lenses independently found that the skill BODY is never the saving — the median SKILL.md is ~4,200 bytes while every workflow agent carries CLAUDE.md (35,457) plus AGENTS.md (6,630), roughly 10.5k tokens. The only real win is displacing intermediate EVIDENCE, and that win is orchestrator-window-local; nobody has measured whether total spend rises. Two further corrections follow: several candidates already delegate natively (research, report, work, brainstorm), so their fan-out tokens are already outside the orchestrator and a workflow buys determinism rather than tokens; and the council precedent proves the skill file does not shrink, because the by-hand fallback must survive for every runtime that .claude/workflows/ never reaches (package.json:10). So the honest case for this programme is enforcement and wall-clock, with token savings real but narrower than stated. Consensus: proceed with conditions, on a short leash. All five lenses agree that a large majority of the catalog stays as skills — twelve of nineteen are never in the synthesized roadmap and seven of those are unanimous across all five lenses (wish, quick, genie, genie-hacks, omni, authoring, refine). All five agree on the exclusion mechanics: no mid-run user interaction, no clock (scripts/workflows-meta.test.ts forbids Date.now, argless new Date() and timers, which makes quick structurally impossible), one-level nesting (.claude/workflows/README.md:23) against a four-deep lifecycle chain, and agent() returning null with no filesystem or process access to discover what a dead agent left behind. All five agree the conversion unit is three artifacts, not one: the script, a thinned front door that keeps a working by-hand dispatch inside the 40-90 line house range, and a single-source parity test. The convergent now set is small and read-only: skill-audit as the workfly dogfood, then research, then docs' audit half. Everything mutating — work, fix, dream, merge — is later or never, and the two skills whose own text forbids the mechanism (quick's "No fan-out and no group ceremony", verify's "a report from another agent is a pointer to evidence, not the evidence") are excluded by construction.

Risks:
- Nineteen front doors plus nineteen scripts plus nineteen parity tests is a tripling of the surface the skills channel currently carries, and only the skill half reaches a host (package.json:10). The steady-state maintenance cost lands on every future edit to a lifecycle contract, which must now be made in two places and re-pinned in a third.
- Silent degradation is the dominant failure mode: agent() returns null and the script has no filesystem or process access to find out why (scripts/workflows-meta.test.ts). In review, a crashed security lens filtered out with .filter(Boolean) reads as 'no security findings' and can turn a FIX-FIRST into a SHIP unless every panel carries council.js:202's quorum floor.
- Prompt-quality regression: the retired-vocabulary ban, the skill-relative resource check and the real-command-name check in scripts/skills-lint.ts govern skills/**/*.md only. Conversions move the executable prompt text out from under the only linter that has ever caught drift in it.
- Divergence between front door and workflow. scripts/council-workflow-parity.test.ts works because council has one roster and a regex can find it. Prose contracts like review's severity table or work's card-conversation table have no such single extractable structure, so parity for those conversions will be a string-containment test that passes while the two texts drift in meaning.
- Runtime fragmentation: a genie user on Codex or DSH runs the skill body, a genie maintainer inside this checkout on Claude Code runs the workflow. Two execution paths for the same named procedure means bugs reproduce on one and not the other, and dsh-workflow-fork is itself FIX-FIRST.
- Token regression on small fan-outs. At ~11k tokens of CLAUDE.md/AGENTS.md per agent, a three-agent workflow over small inputs costs more than reading the inputs inline. Converting for the sake of the programme rather than for measured savings will make the orchestrator slower and more expensive, not less.

Risks:
- Converting a lifecycle skill moves the procedure from the surface that ships everywhere (skills.sh → ~/.agents/skills, ~/.claude/skills) to a surface that exists only inside a genie checkout on Claude Code. If the front door's by-hand fallback is thinner than the workflow, every Codex/DSH/non-checkout user silently gets a degraded skill. This is the single largest delivery risk and it compounds with each conversion.
- Nesting collision on the lifecycle chain: dream → work → review → fix is four levels against a one-level limit. The likely failure mode is not an error but a quiet collapse into one enormous script that is harder to review than the four skills it replaced, with the fix loop's counters and the work moment table duplicated inside it.
- Mutating conversions have no cheap rollback. A read-only conversion rolls back by deleting the .js; work and dream can fail mid-run having already moved HEAD, written card timeline events into genie.db/roadmap.json, and — for dream — opened or merged PRs to dev (skills/dream/SKILL.md:35,58).
- No mid-run interaction converts an ambiguity into a failed run. In work, the rulings rule (skills/work/SKILL.md:39) requires stopping for irreversible, destructive or security-sensitive actions; a workflow either aborts mid-mutation or the rule is weakened by omission. Same for fix's promotion gate (skills/fix/SKILL.md:37), which demands a recorded human ruling.
- The catalog test is a hygiene lint, not a security boundary — the council run said so directly (council-2026-09-15.md:123: it evaluates the meta block with `new Function(...)()`, and its token regexes are 'trivially bypassable'). Nineteen conversions means nineteen files of contributor-editable prompt text executed with real, paid subagents.
- Per-agent cost is unmeasured against the inline baseline. The 583k/6 figure is a total, not a comparison; if CLAUDE.md injection dominates a short agent, small fan-outs could cost more than they save, and the whole program would be optimizing the wrong number.
- Each conversion adds a second source of truth (skill prose + script) that only a bespoke parity test holds together. Nineteen parity tests is real maintenance debt, and a weak parity test is worse than none because it certifies drift as checked.
- Contract-test churn on review/work/fix/dream touches scripts/release-docs.test.ts and scripts/task-conversation-contract.test.ts, both release gates whose assertions were themselves the applied output of prior council runs. Editing them to permit a thinner skill risks deleting a hard-won invariant along with the prose that carried it.

Key evidence:
- Distribution is the decisive product fact: workflows are repo-scoped only. Plugins cannot ship them — 'plugins cannot ship workflows — component fields are skills, commands, agents, hooks, mcpServers...' (.genie/brainstorms/council-workflow/DESIGN.md:58) — and the old install-time stamp to ~/.claude/workflows/council.js is declared dead and was deleted on the dogfood host (.claude/workflows/README.md:32-35). Skills ship everywhere through skills.sh (CLAUDE.md, skills.sh gotcha); workflows reach this repo and, once dsh-workflow-fork lands, a DSH body. So every conversion optimizes genie's own dogfood while every external user keeps the by-hand skill path.
- .claude/workflows/README.md:1-6 states the catalog is canonical and git-tracked, and skills/council/SKILL.md:12 shows the front-door shape in a single paragraph: name the saved workflow, relay `report` unchanged, list `notConvened`, and keep the by-hand dispatch for runtimes without a workflow surface. That paragraph costs about five lines — the budget every other candidate must find inside the 40-90 house range (skills/authoring/SKILL.md:33).
- Per-agent preamble is a real, measurable cost against the token thesis: CLAUDE.md is 35457 bytes and AGENTS.md 6630 bytes (measured with wc -c), roughly 11k tokens injected into every workflow agent. A five-agent fan-out spends ~55k tokens before doing any work, so a conversion only pays where each agent's suppressed intermediate output clearly exceeds that — true for research, skill-audit, review, docs, dream; false for refine, genie, authoring, genie-hacks.
- Six of the nineteen skills are already at or near the 90-line ceiling: omni 84, dream 82, review 81, work 80, wish 78, quick 74 (wc -l over skills/*/SKILL.md). Adding a front door while keeping the by-hand fallback is a real scope risk for exactly the skills with the largest fan-out.
- The mid-run-silence constraint bites hardest on the highest-value candidates: brainstorm's numbered frontier rounds (skills/brainstorm/SKILL.md:22), work's stop-and-ask list (skills/work/SKILL.md:39), omni's six distinct authorities (skills/omni/SKILL.md:82), dream's authority-gated merge (skills/dream/SKILL.md:12), fix's promotion gate requiring a recorded human ruling (skills/fix/SKILL.md:37), and skill-audit's retirement confirmation (skills/skill-audit/SKILL.md:49).
- quick is contract-impossible, not merely unwise: the deadline is the skill (skills/quick/SKILL.md:20,28,36,40) and the workflow contract bans Date.now, argless new Date() and timers (scripts/workflows-meta.test.ts FORBIDDEN list).
- Nesting is one level (.claude/workflows/README.md:23), which forces an ordering decision rather than a free-for-all: work -> review -> lens panel and dream -> work -> review are both three levels. review is worth more as a workflow than work is, so work and fix must stay skills that invoke it.
- Drift control is per-conversion work, not free: council needed a dedicated single-source guard (scripts/council-workflow-parity.test.ts asserts the roster lives only in council.js and the skill carries none), and scripts/task-conversation-contract.test.ts separately pins wording in work (lines 14,25,46), review (33,54) and fix (40,62).
- agent() returns null on failure (.claude/workflows/README.md:21-22). For assess-only council that is a reported absence; for a repo- or external-mutating workflow (fix, dream, work) a null is a half-applied change with no operator present, which is why every mutates:repo/external candidate is later-or-never in this assessment.

Risks:
- Two-path product split: converted skills get the fast path in the genie repo and the degraded by-hand path everywhere else. With no delivery mechanism (DESIGN.md:58; README.md:32-35) the majority of genie users — who run skills in their own repos — experience conversion as pure text churn in the skill they read.
- House-size squeeze: review (81), dream (82), work (80), omni (84) are within nine lines of the ceiling that skills-lint and the authoring contract enforce. The likely failure mode is content being pushed into references/, which degrades exactly the fallback runtime the constraint exists to protect.
- Drift-guard tax: each conversion needs its own parity test in the council shape, plus edits to scripts/task-conversation-contract.test.ts and scripts/release-docs.test.ts where they pin wording. Nineteen conversions would mean nineteen new guards; the value of a conversion must clear that maintenance cost, which for refine, genie, merge and authoring it does not.
- Silent-null mutation: a workflow that mutates the repo or an external system and whose agent returns null leaves a half-applied change with nobody watching. This is a new failure class the catalog has never had, since both existing entries are assess-only.
- Spawn-cost inversion: for small skills, N agents x ~11k tokens of injected CLAUDE.md/AGENTS.md can exceed the intermediate output being suppressed, turning a 'token optimization' into a regression. This is a measurable risk, not a theoretical one.
- Losing the interruptible orchestrator: today a user can redirect work, fix or dream mid-run. Converting any of them trades that for speed, and the skills' own safety text (stop-and-ask, promotion gate, authority confirmations) is written on the assumption it exists.
- Over-conversion as scope creep: the decision frames all nineteen as candidates because 'they were written to be run as such'. Several were not — authoring and verify are specifications whose value is being resident in the caller's context, and refine is already a single delegation.

Conditions:
- Convert research first as the workfly dogfood and land nothing else until it ships with its own parity test in the scripts/council-workflow-parity.test.ts shape. It is the cheapest failure (a discardable notes file) with the clearest structure (N source-scoped investigators plus one synthesis).
- Every converted skill keeps an explicit by-hand dispatch section and stays inside the 40-90 house range (skills/authoring/SKILL.md:33). If a conversion cannot fit, refuse the conversion rather than raise the ceiling or push the fallback into references/.
- No skill declaring mutates: repo or mutates: external converts until agent()-null has a defined recovery for a half-applied change. That defers fix, dream, work, merge, quick and omni behind an explicit design decision.
- No workflow performs an act requiring authority it cannot obtain: no merging, no PR creation against a grant it did not receive in args, no live external message. dream converts only with the wish selection and the merge authority frozen in args by the front door, and with its four-row evidence gate (skills/dream/SKILL.md:40-46) as the return schema so an unfillable row mechanically yields blocked.
- Each conversion ships its single-source guard in the same change, and updates scripts/task-conversation-contract.test.ts wherever it pins the converted skill's wording (work 14/25/46, review 33/54, fix 40/62).
- Answer distribution explicitly before a third conversion lands: either dsh-workflow-fork ships (currently FIX-FIRST per .genie/INDEX.md:20) or the catalog README states plainly that these workflows are genie-repo-only and the skill body is the supported path everywhere else.
- Order the second wave by recurring value, not by structural neatness: skill-audit, then review, then docs, then report, then dream last. review pays back on every group of every wish and therefore carries the highest regression risk, so it follows a proven builder rather than leading it.
- Before converting review or dream, resolve whether a workflow agent can see the Workflow tool. If it cannot, the one-level nesting limit is binding and work/fix must be confirmed as permanent skills in their own text, not left implicit.

Unknowns:
- Whether Claude Code exposes the Workflow tool to a workflow agent. This is load-bearing for review-inside-work and for dream's per-wish workers; the catalog documents only 'workflow() nests one level only' (.claude/workflows/README.md:23) and says nothing about the tool's availability inside an agent.
- Actual token cost per workflow agent spawn versus an inline skill step. I measured the injection (CLAUDE.md 35457 bytes + AGENTS.md 6630 bytes) but not what the runtime actually charges per spawn, including any cached-prefix discount. Without that number the break-even point for a small fan-out is a guess, and it decides whether report and docs are worth converting at all.
- Whether skills.sh or any future channel could deliver .claude/workflows to a user's repo. Nothing in the installer references the catalog (grep over src/ and scripts/ found only plugins/dsh-genie-board reading it), and DESIGN.md:58 says plugins cannot. If this stays true, the compatibility argument permanently caps how many conversions are justified.
- Whether the DSH executor reads the same directory in practice. .claude/workflows/README.md:4-6 asserts it will, but dsh-workflow-fork is FIX-FIRST with a seam-comparison gate still open (.genie/INDEX.md:20), so the 'runs unmodified on any body' claim is currently a plan, not a shipped fact.
- Whether a workflow's return value can carry a value byte-for-byte unaltered through to a caller's command. brainstorm's stamp consumes the reviewer's own reviewed-sha256 and rejects a recomputed one (skills/brainstorm/SKILL.md:44); if the workflow boundary normalizes or truncates, that conversion is unsafe.
- How a partially-failed fan-out should be surfaced to the user for an audit skill. council reports notConvened and refuses below three lenses; the right floor for skill-audit (a shard that never reported means skills silently unaudited) is undecided and would be a real correctness gap.

Key evidence:
- Per-agent fixed overhead measured: CLAUDE.md is 35,457 bytes and AGENTS.md 6,630 bytes (wc -c), roughly 10.5k tokens injected into EVERY workflow agent spawn. The largest SKILL.md body, skills/work/SKILL.md, is 9,162 bytes (~2.3k tokens) and the median is ~4,200 bytes (~1.0k). One workflow agent therefore costs 5-15x the entire skill body it is meant to displace.
- Corollary and central finding: unloading skill TEXT from the orchestrator is never the win. The only real win is displacing INTERMEDIATE EVIDENCE — file reads, diffs, command output, lens reports. A workflow agent breaks even only if it consumes or produces more than ~10.5k tokens the orchestrator would otherwise have held.
- council.js:196-207 spawns six agents (five lenses plus synthesis), so one council run pays roughly 63k tokens of CLAUDE.md+AGENTS.md injection before any lens reads a file. This is the measured price of the precedent and the baseline every conversion must beat.
- council.js:152-187 assembles the entire final report with JS string concatenation. Every line render() produces costs zero model tokens. This is the one uniformly free win available to any skill with a fixed-shape deliverable: report/SKILL.md:29-36, dream/SKILL.md:65-80, verify/SKILL.md:53-55, skill-audit/SKILL.md:36-44, review/SKILL.md:54-65.
- Skills that ALREADY delegate get near-zero marginal token win, because their subagents already pay the CLAUDE.md injection today: work/SKILL.md:18-22, research/SKILL.md:13-14, report/SKILL.md:23, brainstorm/SKILL.md:24, dream/SKILL.md:29. For these the workflow changes who decides the fan-out, not where the tokens go.
- skill-audit has the largest un-displaced payload: the 19 shipped SKILL.md files total 62,656 bytes (~16k tokens), all of which currently enters the orchestrator (skills/skill-audit/SKILL.md:28-31). It also has a mechanical shard key and an assess-only contract (skill-audit/SKILL.md:10), making it the cheapest-failure dogfood.
- review's lens panel carries 13,418 bytes across seven files under skills/review/references/lenses/ and is structurally identical to council (review/SKILL.md:38-50) — the clearest second conversion, but only the panel: a single-target review (review/SKILL.md:24-36) is one agent, where a workflow ADDS ~10.5k and saves nothing.
- The no-clock rule is a hard, concrete blocker, not a stylistic one: scripts/workflows-meta.test.ts:13-15,20 forbids Date.now, argless new Date() and all timers. That makes quick's minute-windowed contract (quick/SKILL.md:20,26,30,38) and dream's CI polling (dream/SKILL.md:34) inexpressible.
- workflow() nests one level only (.claude/workflows/README.md:23), while work -> review -> fix -> review is at least three (work/SKILL.md:48-50, fix/SKILL.md:18-19). work cannot be a full workflow; fix can host a review agent but never a review workflow.
- scripts/task-conversation-contract.test.ts:14-40 pins exact wording inside work, review and fix SKILL.md. Every conversion touching those three costs a contract-test migration, for which scripts/council-workflow-parity.test.ts is the precedent pattern.
- scripts/release-docs.test.ts:15-35 pins all nineteen skill directories as SHIPPED_SKILLS, so no skill can be deleted — only thinned. Conversion is additive by construction, which bounds the downside.
- Workflows are repo-scoped and Claude Code-only (.claude/workflows/README.md:3-6) while skills ship to every runtime through skills.sh, so each front door must retain a by-hand fallback (the council skill does, skills/council/SKILL.md:12). That caps how far any body can shrink and therefore caps the body-side token saving at roughly 1-2k per skill.

Risks:
- Injection amplification: each conversion multiplies the ~10.5k CLAUDE.md+AGENTS.md payload by its agent count. A seven-lens review panel costs ~84k tokens of injection alone. Converting broadly could raise total token spend even while the orchestrator's own context shrinks — the orchestrator gets cheaper, the bill gets larger. Nobody has measured the aggregate.
- CLAUDE.md is 35KB today and growing (its Gotchas section alone is most of the file). Every future line added to it silently taxes every agent of every workflow. The catalog creates a coupling between repo documentation size and workflow cost that nothing currently monitors.
- Converting already-delegating skills (research, report, work's dispatch) buys determinism, not tokens. Presenting those as token optimizations would misattribute the benefit and could justify conversions whose real cost is lost flexibility.
- agent() returns null with no retry (.claude/workflows/README.md:21-22). For assess-only workflows a null is a quorum question (council.js:202); for any mutating workflow it is a half-finished repo state the script cannot repair. This is why merge, fix, work and dream carry disproportionate risk.
- Name-shadowing hazard scales with the catalog: a stale ~/.claude/workflows/council.js resolved ahead of the repo copy on 2026-09-15 (.claude/workflows/README.md:30-35). Nineteen names is nineteen shadowing opportunities, and a silently stale workflow is far harder to notice than a stale skill.
- Structured-output overhead is not free: a schema forces each agent to serialize findings into JSON, which for prose-heavy findings (review's severity/trigger/impact/evidence/correction, review/SKILL.md:67) can cost more output tokens than the plain text it replaces. council's schemas are terse; a naive conversion's may not be.
- Front doors that keep the full by-hand fallback (required for non-Claude-Code runtimes) can end up LARGER than the original skill — council/SKILL.md is 3,698 bytes and still carries the fallback dispatch. A conversion can plausibly increase always-loaded description cost while decreasing nothing.

Conditions:
- Instrument before converting the second skill. Run the existing council workflow once with token accounting and publish the real per-agent injection figure. My ~10.5k estimate is derived from file sizes, not from a token bill, and the entire break-even analysis rests on it.
- Adopt an explicit break-even rule in .claude/workflows/README.md: convert a stage only when its agents consume or produce more evidence than their own injection costs (roughly 10k tokens each). Refuse any conversion that wraps a single agent — refine, wish's plan review, quick's executor all fail this test.
- Dogfood workfly on skill-audit, not review. Its evidence set is the largest un-displaced payload in the catalog, its shard key is mechanical, and it is assess-only by contract (skill-audit/SKILL.md:10) so a failed run mutates nothing. review is the better second conversion because it must also carry a contract-test migration.
- Render every fixed-shape deliverable in JS, following council.js:152-187. This is the only uniformly free saving available and should be a stated requirement of the contract, not left to each author.
- Convert review as a panel-only workflow (review-panel.js), leaving the single-target design/plan/PR pipelines in the skill. Name that split in the workflow's meta.whenToUse so callers cannot route a one-target review through it.
- Every conversion that thins work, review or fix ships a parity test in the same change, modelled on scripts/council-workflow-parity.test.ts, replacing whatever scripts/task-conversation-contract.test.ts assertions the thinning invalidates. No thinning lands with a red contract test.
- Cap the catalog. Stop after the four 'now' conversions and re-measure aggregate token spend before approving the 'later' four. The marginal skills are all medium-or-lower win with real risk, and the shadowing hazard grows with catalog size.
- Keep every front door's by-hand fallback and measure the resulting body size. If a converted skill's SKILL.md does not shrink, record that the conversion was bought for determinism and speed, not tokens.

Unknowns:
- The actual token cost of a workflow agent spawn. I measured CLAUDE.md at 35,457 bytes and AGENTS.md at 6,630 bytes, but whether the runtime injects them in full, truncated, summarized, or cached across agents in one run is undetermined — and prompt caching across the five parallel lenses would change the economics by roughly an order of magnitude in the workflow's favour.
- Whether the Workflow tool is exposed to a workflow agent. .claude/workflows/README.md:23 documents one nesting level via workflow(), but not whether an AGENT can itself invoke a workflow. If it can, fix and work become far more tractable; if it cannot, the nesting blocker on work is permanent.
- Whether output-token cost of schema serialization exceeds the plain prose it replaces for finding-heavy lenses. council's schemas are terse; review's finding shape (review/SKILL.md:67) is not.
- Whether agent() failures are observably distinguishable from an agent that legitimately found nothing. council handles this by quorum count (council.js:202), but a verify workflow must not report a crashed check as a passing one, and the contract does not say whether the distinction is available.
- Actual wall-clock speedup of parallel() versus a model-driven fan-out on this runtime. I assert a real speed win where skills currently serialize, but no timing evidence exists in the repository for either path.
- Whether the DSH executor (dsh-workflow-fork, a separate FIX-FIRST wish per the constraints) injects the same CLAUDE.md payload. If DSH's injection differs, per-conversion economics are runtime-dependent and this entire assessment holds only for Claude Code.
- Aggregate frequency of invocation per skill. A high token cost per run is acceptable for a skill run weekly (skill-audit) and unacceptable for one run many times per session (genie routing) — no usage data was supplied, so my priority ordering assumes rather than measures that distribution.

Key evidence:
- The premise that conversion saves tokens is unsupported and probably inverted: each workflow agent receives CLAUDE.md (35,457 bytes, 249 lines) plus AGENTS.md (6,630 bytes) — measured with wc — so a five-lens fan-out injects roughly 210KB of instruction context to replace a skill body of 43-84 lines (whole corpus: 1167 lines across 19 files). Orchestrator-window savings and total-token savings are being conflated.
- The isolation benefit already exists without workflows. Every candidate skill already instructs native delegation: brainstorm SKILL.md:24 ('delegate a read-only scout through the runtime's native delegation surface'), report:23, research:14, work:18, fix:10. The marginal gain of a workflow is a deterministic roster, not context isolation.
- The 'workflow agents run on Opus' premise is not implemented anywhere in the catalog: neither .claude/workflows/council.js nor .claude/workflows/pm-ledger-verify.js sets a model; pm-ledger-verify.js:89 sets only effort: 'high'.
- Discovery is unreliable and hostile to a build-verify loop. .claude/workflows/README.md records that a 2026-09-15 probe resolved the name `council` to a stale user-scope copy, and .genie/wishes/workflows-catalog/WISH.md:99 records that the registry is built at session start, so the recorded run had to be invoked by scriptPath and 'a fresh session must confirm name resolution'. A builder skill that lands scripts cannot verify them in the session that wrote them.
- Conversion launders procedure text out of every shipped gate. scripts/skills-lint.ts:610-642 walks SKILLS_DIR only, checking frontmatter, directory shape, resource paths, real command names, the retired-vocabulary ban (no allowlist) and the mutates:none fence rule. Nothing under .claude/workflows/ is scanned; scripts/workflows-meta.test.ts checks only JS syntax and forbidden tokens.
- The richest procedures are pinned by contract tests against the SKILL.md text: scripts/task-conversation-contract.test.ts asserts 18 exact strings across skills/work, skills/review and skills/fix. A front door that keeps those strings is not thin and yields no token win; one that drops them moves a tested contract into a Claude-Code-only file.
- Reach is asymmetric and the bridge is not shipped. Skills reach every runtime through skills.sh (CLAUDE.md records 57 agent homes on the dogfood host); workflows are repo-scoped Claude Code only, and .genie/wishes/dsh-workflow-fork/WISH.md:5 is Status FIX-FIRST with a Group 0 kill criterion: 'if neither route can run council.js unmodified within this wish's appetite, the fork stops and the catalog stands alone'.
- The single precedent already produced two plumbing defects the skill form did not have: the string-args defect ec68cd8f (.genie/wishes/council-workflow/WISH.md:6) and the lens attribution indexed after filter(Boolean) (.genie/wishes/workflows-catalog/WISH.md, Scope OUT).
- Hard mechanical blockers exist for specific candidates: scripts/workflows-meta.test.ts forbids Date.now, argless new Date() and all timers, while skills/quick/SKILL.md:20,26,30,38 is built entirely on a 60-minute wall clock and skills/dream/SKILL.md:34 requires CI polling.
- The builder does not exist: `workfly` returns zero hits across the repository. The programme proposes building a builder before a second conversion has been done by hand, against the repo's own Simplicity Gate (skills/brainstorm/SKILL.md:30; skills/wish/SKILL.md:46, justify added machinery with a present requirement or measurement).

Risks:
- Total token spend rises while the metric the decision is measured on (orchestrator context) falls, so the programme reports success while costing more — most acutely for skill-audit, where 19 tiny file reads would each carry a ~42KB injection.
- Every conversion needs its own single-source parity guard. scripts/council-workflow-parity.test.ts is 39 lines holding five lens names and six string assertions for a fixed-roster skill; there is no equivalent shape for work's card-conversation table or fix's escalation matrix, so those conversions would duplicate prose with no drift guard.
- Silent nulls in mutating workflows. .claude/workflows/README.md states agent() returns null on failure or skip. In a converted work or dream, null is indistinguishable from a worker that claimed a card, mutated the repo, opened a PR and then died — exactly the state skills/work/SKILL.md:35 and skills/dream/SKILL.md:40-47 exist to prevent.
- Two-runtime divergence becomes permanent maintenance. The skill must keep a by-hand dispatch for Codex, DSH, Goose and Windsurf (CLAUDE.md, KNOWN_AGENT_SKILL_HOMES), so each conversion creates two implementations of one procedure that drift until a test pins them.
- Nesting is capped at one level (.claude/workflows/README.md) while the lifecycle skills call each other (work → review → fix → review). Converting more than one lifecycle skill can deadlock against the cap, and whether a workflow agent can call the Workflow tool at all is an acknowledged unknown.
- A stale user-scope copy silently shadows a repo copy — it already happened once. At nineteen entries that is nineteen shadowable names in a namespace with no doctor check, which workflows-catalog explicitly deferred in its Simplicity Case.
- Interactive-gate erosion: the cheapest way to make an interactive skill fit the contract is to weaken its user gate. brainstorm's frontier rounds, fix's escalation approval and promotion ruling, skill-audit's retirement confirmation and omni's per-authority confirmations are all pressure points where 'the workflow cannot ask' becomes 'the workflow proceeds'.

Conditions:
- Measure before converting anything else: record one real token count for a workflow-agent spawn against the same step run inline, on this repo with this CLAUDE.md, and publish it in the wish. The whole case rests on a number nobody has.
- Convert at most one more skill — research — and only as a fan-out-core, keeping the full procedure in skills/research/SKILL.md for the by-hand path. Ship it, run it for a week, and record defects the way council-workflow recorded ec68cd8f before authorising a third.
- Do that conversion by hand. Build `workfly` only after two hand conversions have shown a repeated shape, per the repo's own rule that added machinery needs a present requirement.
- Land a `genie doctor` catalog check (stale user-scope shadow, meta.name/file mismatch, orphaned entries) before the catalog exceeds three entries; workflows-catalog deferred it with the trigger 'a second orphan like council.js', and a nineteen-entry catalog is that trigger.
- Extend scripts/skills-lint.ts's banned-vocabulary and real-command scans to .claude/workflows/*.js, or state explicitly in the catalog README that converted procedure text leaves those gates.
- Freeze work, fix, dream, quick and verify as non-candidates in writing, with the mechanical reason recorded per skill, so the list is not revisited by each successive wish.
- Require every conversion to ship a single-source parity test that fails when the skill and the workflow disagree, and refuse the conversion when no such test can be written.

Unknowns:
- Actual token cost of a workflow agent spawn versus an inline skill step on this repo — explicitly unresolved, and it is the load-bearing premise of the entire decision.
- Whether a workflow agent can invoke the Workflow tool at all; nesting is documented as one level via workflow(), which does not settle whether an agent inside a workflow may start another.
- Whether a converted skill's by-hand degradation path is ever actually exercised. council's has shipped since 2026-09-15 with no recorded non-Claude-Code run, so the claim that skills 'degrade gracefully' is untested.
- Whether the Workflow tool is available on the plans and Claude Code versions genie's users run; the retired council-workflow wish recorded a floor (CC >= 2.1.154, paid plan, org disableWorkflows) that the current catalog README does not restate.
- Whether name resolution picks the project-scope file in a fresh session — .genie/wishes/workflows-catalog/WISH.md:99 leaves this open as a criterion a fresh session must confirm.
- Whether agent() distinguishes 'failed' from 'skipped', which decides whether a mutating workflow can ever safely resume.
- Whether skills.sh will eventually ship workflows, which would remove the reach asymmetry and change the answer for several skills I currently oppose.
