## Problem

The Genie Bot's wish path cannot end in a verified PR, because the foundation under it is wrong. It bases on the local HEAD (D1). Its clone's `origin` is the user's checkout and is the only remote identity the wish has (D2). A plain wish's clone still offers push routes, to the user's checkout as `origin` and through the user's global credential helper, while its brief forbids pushing; #3184 (merged 2026-10-28) fixed #3182 for follow-ups scoped by `branches` by adding a `publish` remote, which copies the project's raw remote URL, credentials included when the URL embeds them (D3). Any turn end is "brought back" and shown as Done (D4), and the instructions call a local branch finished (D5). Delivery (program wish 2) cannot add publication on top of that without inheriting each defect. This wish makes the repository binding, the isolated workspace, the persisted wish state, the publication boundary and the evidence explicit. It uses only host capabilities that exist today.

## Approach

Put every mechanical step in host code, where `genie-dsh` already runs git as argv through `execFile` (`plugins/genie-dsh/src/host/git.js`). Agents keep only the work itself. This is the program's thesis (genie-v7 R1-2) applied to the foundation: base resolution, fetch, branch, push lockout, end classification and evidence become tested code, not instructions to an agent. Remote operations run in the user's own repository with the user's own configuration, so no URL or credential is ever copied into the agent's workspace.

Read against genie origin/dev `c3cfa000a`. A first draft was read against a stale local `dev` that predated #3184, which is this wish's own D1 failure in the planning itself.

Alternatives considered:
- **Re-point the clone's `origin` at the real remote** (round-1 design). Lost to reviewer HIGH-1 and HIGH-2. It hands the agent a live push target through the user's global credential helper, and stripping userinfo breaks SSH remotes.
- **Call `genie context` from the plugin** (genie-v7 R1-3 says the CLI is the state core). Lost here, for now. A Bot host does not guarantee `genie` on PATH, and its SHA is the unfetched local one. The plugin mirrors the two-rule branch policy, and a parity test pins it to the CLI's output.
- **Store wish state in the team's `rt.state`.** Lost: `adopt` rebuilds the object on load/refresh (automagik `apps/bots-dsh/src/host/store.js`), and `genie.json` already exists with temp-file-then-rename writes.
- **Worktree instead of clone.** Lost: the clone lives in the team workspace because that is where a task session may write (`plugins/genie-dsh/src/host/genie.js`).

## Simplicity Case

- **Simplest complete design:** one binding resolved per grant (no cache), one fetch in the user's repository, one record per wish in the existing file, live transitions from the event the plugin already receives, and a two-rule branch policy.
- **Added machinery:** startup reconciliation, because D4 is demonstrated and the team keeps only 60 task records (automagik `apps/bots-dsh/src/host/agents.js`). An in-memory claim set, the smallest mechanism that makes the live and startup paths run once (reviewer MEDIUM-1). Evidence entries, because "local commit presented as completion" is a recorded failure and the fix is proof, not prose.
- **Deferred until measured:** a binding cache (trigger: grant latency the user notices), a base override (trigger above), a stored grant (program wish 2), and a CI job (trigger above).
- **Complexity removed:** the "delivered" flag and the unconditional "Done"; any URL rewriting; credential handling in the clone; silent fallback to a stale base.

## Risks & Assumptions

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| 1 | A fetch needs network access, and the user's credentials for a private remote; an offline user can no longer start a wish on a remote-bound repository | Medium | The refusal quotes git's own error, passed through the same password-dropping display form as every recorded URL, and names the fix: run `git fetch <remote> <base>` in the repository and ask again. It uses the same configuration the user's own fetch uses. No-remote repositories keep working in `local` mode |
| 2 | `rt.state.tasks` is not a documented API and could change shape | Medium | It is read only at startup, it is listed in the executable host contract, and a missing or non-object record never yields `lost` or Done |
| 3 | An agent with network access can still push by spelling a URL and credentials itself | Medium | Out of this wish's reach by design: DSH's sandbox is the boundary, and its network rule is the Automagik question recorded in OUT. The lockout removes every route that works by default |
| 4 | The fetch may update the user's `refs/remotes/<remote>/<base>` and always writes `FETCH_HEAD` | Low | The same refs the user's own `git fetch` writes; the branch, HEAD, index and working tree are untouched (T1) |
| 5 | A wish with a 60+ task backlog loses its task record before reconciliation | Low | `lost`, with the branch and evidence kept, and a later live end still classifies it |
| 6 | Size M is at its upper edge: nine deliverables and two new modules | Medium | One package, no host change, and every deliverable has its own fixture; if implementation outgrows M, the publication-boundary check (deliverable 5) moves to program wish 2 first, since nothing in this wish consumes it |

## Success Criteria

- [ ] **T1 fresh base:** upstream `dev` is one commit ahead of the local checkout's `dev`, and the wish branch starts at the upstream tip, with `baseSha` equal to it. The same holds for a single-branch clone whose fetch refspec does not cover `dev`. A `FETCH_HEAD` overwritten by another fetch, or holding a line for another branch, refuses the wish instead of starting it. The repository's checked-out branch, HEAD, index and working tree are unchanged. **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T2 remotes and credentials:** `https://user:token@host/o/r.git` and `https://token@host/o/r.git` are both recorded as `https://host/o/r.git`; `ssh://git@host/o/r.git` and `git@host:o/r.git` are recorded as written; all three give `repoSlug` `o/r`. The repository's remote configuration is byte-identical before and after a wish. The string `token` appears nowhere in `genie.json` or in any text returned to the model, including the refusal for a failing fetch from a token-bearing URL. **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T3 branch policy parity:** local `dev` → `dev`; no `dev` with `origin/HEAD` → its branch; no remote → `local`. In the two fixtures that have a remote, the binding agrees with `bun <genie repo>/src/genie.ts context --plan` (the CLI has no `local` mode, so the no-remote case is not compared). A repository whose `core.sshCommand` is set keeps it: the host adds no `GIT_SSH_COMMAND`. A base the remote lacks is refused, naming the fix. **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T4 local mode:** a repository with no remote runs from local HEAD, the binding says `local`, the outcome never exceeds `local-only`, and `publishAllowed` refuses. **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T5 reconciliation:**
  - A saved `working` wish whose task is `done` at startup transitions exactly once across two loads.
  - A `working` task stays `working`.
  - A missing record becomes `lost` only on a writable host with a tasks record that was read; on a read-only host, or when `resumesDone` reports `readOnly` or `failed`, nothing changes.
  - A live turn end that races the startup pass transitions once.
  - A turn end cut by a restart changes nothing.
  - A task whose first turn ended before the entry was saved is classified right after the save.

  **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T6 honest outcomes:** `done` with commits → `local-only`, and the branch is fetched back. `done` with none → `no-change`, and nothing is fetched. `stopped` or `failed` with commits keep their outcome word and are fetched back. A scoped follow-up that commits only on a given branch is `local-only` and that branch is fetched back, so #3184's own test keeps passing unchanged. A `blocked` live turn end changes nothing. No v2 state renders as `Done`. A v1 entry still running at upgrade is classified from its recorded `base`. **Proof:** `plugins/genie-dsh/test/foundations.test.js`, `plugins/genie-dsh/test/genie.test.js`.
- [ ] **T7 publication boundary:** in a plain wish's clone, `git push origin wish/<slug>` exits non-zero and the user's repository does not gain `refs/heads/wish/<slug>`; the clone's local config carries `remote.origin.pushurl` and an empty `credential.helper`; there is no `publish` remote. A push to the bare upstream's path from the clone succeeds in the fixture, which documents that the sandbox, not this lockout, is the boundary against a hand-spelled URL. A scoped follow-up still gets `publish` and its #3184 brief. An `http(s)` remote URL with a password, or with a token as its username, refuses a scoped grant, and the secret appears nowhere in the clone's config or in `genie.json`. A scoped grant naming `binding.base` is refused. `publishAllowed` refuses an absent grant, one for another `repoSlug` or base, and a `local` binding, each naming the user action. `grant_wish` exposes no argument that reaches a grant. **Proof:** `plugins/genie-dsh/test/foundations.test.js`.
- [ ] **T8 host contract:** the test fake throws on any `rt` or `ctx` member not in the README table, and the full suite passes under it. **Proof:** `plugins/genie-dsh/test/genie.test.js`.
- [ ] **T9 compatibility and words:** a v1 `genie.json` loads with every wish kept and renders as before. The brief no longer has an unexplained "Do not push, merge". The instructions no longer say "merge it when they are happy" for an unpublished branch. **Proof:** `plugins/genie-dsh/test/genie.test.js`.
- [ ] **Gate:** in `plugins/genie-dsh`, `DSH_HARNESS=<a DeepSeek Harness install, e.g. /Applications/Automagik.app/Contents/Resources/runtime> npm test` exits 0, with every test passing on the PR head (baseline on origin/dev `c3cfa000a`: 21 tests, 20 pass, the one failure being the race deliverable 9 replaces), and its output is quoted in the PR body. `bun run check` at the repository root exits 0. CI on both legs is green, which covers the root gate only (OUT: no CI job runs the plugin suite). **Proof:** the PR body and its checks.
