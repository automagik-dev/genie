# Claude Fable 5.2 overlay

Loaded after `claude.md` when the destination is a worker prompt for Claude Fable 5.2 (`--target fable`): the frontier model for judgement roles, such as the Socratic questioner in a council, a final judge or a synthesis, and for long autonomous stages. It selects guidance, not a runtime model. Official sources checked 2026-11-13: [Fable 5.2 overview](https://platform.claude.com/docs/en/models/fable-5-2/overview) and [Fable 5.2 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2). The following is our concise adaptation, not vendor quotation. The target is a worker inside a saved workflow whose agent returns a JSON schema; apply each clause only where the stage shape fits.

## Add when the stage fits

- **Finish the whole task, for unattended multipart stages:** the model carries long work with little guidance on method once the goal is clear, but it can end a turn early by listing what is left, offering to continue, or stopping at an ordinary obstacle such as an error, a timeout, a locked file or an empty result. Say that nobody is watching or can answer mid-task, so asking "Shall I…?" blocks the work; ordinary obstacles are diagnosed and worked through with the access available. Reversible steps that follow from the request go ahead; the stops that stay are destructive actions, genuine scope changes, a deliberate blocker such as a file marked not to be touched or access intentionally withheld, and any confirmation the prompt already names. A decided step is run, not announced, and the turn does not end on a plan or a promise while work is owed. Before a command that changes system state, check that the evidence supports that specific action. Leave this out where a person answers mid-task.
- **Assessment stages:** when the input describes a problem or asks a question, as for a judge or a Socratic questioner, the deliverable is the assessment: report the findings and stop, with no fix applied.
- **Code ownership, for coding stages:** say whose code it is. Where the caller wants structure improved, say the code base is the model's own and its design is up to it; the model then consolidates duplicated code and may make related fixes without being asked, at roughly 70–80% more output tokens, so review the reported diff and summary. Where the user owns the code and wants it changed as little as possible, leave that sentence out; a scope rule does not cancel it.
- **Scope is the deliverable, for stages that produce work:** the request, or the plan the caller approved, sets the scope; the worker does not narrow, widen or swap it. Routine judgement calls are the worker's own; a real concern is said in a sentence while the work continues under a stated assumption. If one part is blocked, every other part is finished and the gap is named with its reason. Cleanup or docs nobody asked for is a suggestion at the end, not a change.
- **Changes and tests, for coding stages:** a pre-existing bug, a performance concern or behavior the task does not mention is reported as a follow-up, not fixed, unless the requested behavior cannot work without it. An ambiguity takes the reading the wording and the code most directly support, stated in the result. Scratch checks need not be kept; tests are committed only where the task asks for them or the repository keeps them for this kind of change, sized like their neighbors. Every requested behavior is still delivered in full.
- **Keep a reader informed, for stages a person watches:** ask for a line before the first tool call, brief updates while working, and a closeout that stands on its own: what was found, what was done and what comes next. Where the client hides tool output, say so. If the runtime cannot append a turn-scoped reminder, add one sentence asking for a one-line update every few tool calls; the opening and recap text adds roughly 20% output tokens.
- **Subagents, for stages that delegate:** say what a subagent adds to the session's cost, when delegation is worth it and when it is not, and how to brief one. Review standing delegation instructions before adding more; at `xhigh` and `max` the model may start subagents to review its own work.
- **Reports and handoffs, for stages a person reads after long work:** write for an intelligent reader who has not seen the tool calls or files: self-contained, key points first, no undefined references. Use plain words, short sentences, one idea per sentence, active voice and the same word for the same thing; flowing prose where ideas connect, bullets for separate items. Remove style rules the reader no longer needs, especially hard limits that make prose choppy.
- **Caution that has piled up, for stages carrying notes or memories:** delete cautions whose reason no longer holds; name the routine steps that need no approval instead of saying "act freely"; narrow a "stop and review at the first error" rule that blocks autonomous work; write "ask before deleting files" rather than "never delete files", and make an approval rule name the actions it covers. Risky or irreversible actions keep their confirmation step.

## Remove when present

- "Hold all findings for the final response" and other lines that suppress narration.
- Anti-formatting rules written to curb bullets and bold in earlier models, when they are tuning rather than a deliberate format restriction. An explicit minimal-format request survives.
- "Think very hard" style lines, and "answer directly without deliberating" style lines: effort is the control, and the latter does not stop thinking at `medium` and above.
- Any request to reproduce its internal reasoning or a chain of thought in the answer. It invites `reasoning_extraction` refusals; read reasoning from thinking blocks with `display: "summarized"` instead. Keep a user-facing rationale, evidence or finding field the output schema requires.
- "Treat that answer as done" lines, where the model should keep re-examining its earlier answers.
- A token budget shown to the model, unless the task is to configure one; it changes how much the model spends.

## Report, never inject

Effort (default `high`; rerun the sweep rather than carrying over one tuned on Fable 5.1 or Opus 5.5. `low` suits well-specified and high-volume work and, on coding evals, scores close to Fable 5.1 at higher effort; `medium` suits interactive coding and everyday work; `high` suits hard coding, research, agentic work and long unattended runs; reserve `xhigh` for a measured gain and `max` for measuring the ceiling or a rare task where time and tokens do not matter; at either level, a long deliverable needs a `max_tokens` with room for thinking plus the reply. Above `high` gains are uneven, and effort has little effect on reply length. Per-message effort can change levels mid-conversation and keep the cache). Progress notes reach a reader only with `thinking.display: "updates"` or `"summarized"`. The history stays append-only: assistant turns go back exactly as returned, a per-turn reminder is a turn-scoped system message appended fresh each turn, instruction or tool changes are mid-conversation system messages, and a client-side compaction replaces the whole history with one summary. On this model a failed prefix check is a 400 error by default; `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` is a stopgap that can raise output tokens. Subagent tool descriptions, thinking display, per-message effort, mid-conversation system messages and prefix-mismatch behavior are harness settings. Never write these controls, or placeholders for them, into the prompt body.
