# Claude Fable 5.1 overlay

Loaded after `claude.md` when the destination is a worker prompt for Claude Fable 5.1 (`--target fable`): the frontier model for judgement roles, such as the Socratic questioner in a council, a final judge or a synthesis, and for long autonomous stages. It selects guidance, not a runtime model. Official source checked 2026-10-01: [Fable 5.1 prompting guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1). The following is our concise adaptation, not vendor quotation. The target is a worker inside a saved workflow whose agent returns a JSON schema; apply each clause only where the stage shape fits.

## Add when the stage fits

- **Finish the whole task, for unattended multipart stages:** the model carries long work with little guidance on method once the goal is clear, but it can end a turn early by announcing the next step or asking permission for work already requested. Say that nobody is watching or can answer mid-task, so asking "Shall I…?" blocks the work. Reversible steps that follow from the request go ahead; the stops that stay are destructive actions, genuine scope changes and any confirmation the prompt already names. A decided step is run, not announced, and the turn does not end on a plan or a promise while work is owed. Before a command that changes system state, check that the evidence supports that specific action. Leave this out where a person answers mid-task.
- **Assessment stages:** when the input describes a problem or asks a question, as for a judge or a Socratic questioner, the deliverable is the assessment: report the findings and stop, with no fix applied.
- **Scope is the deliverable, for stages that produce work:** the request, or the plan the caller approved, sets the scope; the worker does not narrow, widen or swap it. Routine judgement calls are the worker's own; a real concern is said in a sentence while the work continues under a stated assumption. If one part is blocked, every other part is finished and the gap is named with its reason. Cleanup or docs nobody asked for is a suggestion at the end, not a change.
- **Changes and tests, for coding stages:** a pre-existing bug, a performance concern or behavior the task does not mention is reported as a follow-up, not fixed, unless the requested behavior cannot work without it. An ambiguity takes the reading the wording and the code most directly support, stated in the result. Scratch checks need not be kept; tests are committed only where the task asks for them or the repository keeps them for this kind of change, sized like their neighbors. Every requested behavior is still delivered in full.
- **Targeted edits, for stages that edit files:** change the part that changes instead of rewriting the whole file, unless the file is short or most of it changes.
- **Batching, for coding and command loops whose next reads are implied:** list privately what is needed next, then request every item that does not depend on another's result in one response.
- **Verify names, for stages with search tools:** a name the model does not confidently recognize, or one from a fast-moving field such as AI models and developer tools, is the thing to check: search before answering, with the name as written in at least one query. Familiarity is not a reason to skip the search.
- **Quoting, for stages that summarize sources:** restate each source in the worker's own words and mark any exact wording as a quotation. If that is not enough, one complete correct example (the request, the response, a sentence on why it is correct) does more than further rules.
- **Prose a person reads:** ask for direct statement instead of metaphor and flourish (mannered prose), with shorter sentences and paragraph breaks. Where structure helps, say when lists are wanted: the reader asked, or the content has several parts. Conversational replies stay plain prose.
- **Lesser-known languages, for coding stages:** say what the language is and how it works, or point to its documentation; it makes a safeguard false positive less likely.

## Remove when present

- "Hold all findings for the final response" and other lines that suppress narration.
- Anti-formatting rules written to curb bullets and bold in earlier models, when they are tuning rather than a deliberate format restriction. An explicit minimal-format request survives.
- "Does this compile without errors?" standing in for a correctness check; ask whether there are bugs. A compile check the task requires survives.
- Rules that make a lead stop and wait for each subagent before doing other work, unless its next step needs that result.
- "Think very hard" style lines that stand in for effort; effort is the control.

## Report, never inject

Effort (default `high`; sweep `low`, `medium`, `xhigh` and `max` on the caller's own evals, and redo any sweep made on Fable 5, since level names do not carry across models). `medium` roughly matches Fable 5 at lower cost, and `low` is worth comparing wherever a smaller model at higher effort is the alternative. At `low` the model searches less: raise effort for the turns that need fresh facts. Reserve `xhigh` and `max` for a measured gain; a long deliverable there needs a `max_tokens` with room for thinking plus the reply, and the guide's single-limit note appended with the real value. Progress notes reach a reader only with `thinking.display: "updates"`. The history stays append-only: assistant turns go back exactly as returned, a per-turn reminder such as the batching line is a turn-scoped system message appended fresh each turn, instruction or tool changes are mid-conversation system messages, and a client-side compaction replaces the whole history with one summary. A note that the reader cannot see tool output, a subagent tool that returns at once plus a separate wait tool, crop tools for dense images, and removing tools that return base64 are harness settings. Never write these controls, or placeholders for them, into the prompt body.
