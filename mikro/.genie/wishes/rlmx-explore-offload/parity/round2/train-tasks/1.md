## Question (authored for the training suite)

```text
In this repository a Python REPL block can call rlm_query() to spawn a child rlmx run. I need to know exactly what the parent controls about that child and what it does not. Which source lines decide (a) how many children can run at once, (b) what iteration cap and depth ceiling the child is handed, (c) how the child is spawned relative to the parent's process group, and (d) what decides the model the child ends up running on? Answer with a path:line citation for every claim.
```

## Reference answer (authored, and the source of the checklist)

```text
Four separate mechanisms, none of which is the agent's own config.

**Concurrency.** A batched fan-out is capped at four concurrent children: `src/llm.ts:667` sets MAX_CONCURRENT to 4, so nine prompts run as 4 + 4 + 1 in three blocking waves.

**Budget handed down.** The per-request child options are assembled in the parent's LLM-request handler. The iteration cap is passed straight through, unreduced, at `src/rlm.ts:436` — a child gets the *same* cap as its parent, so a 4-way fan-out multiplies model turns rather than dividing them. The recursion ceiling comes from the ambient config, not the agent: `src/rlm.ts:438` hands the child `config.budget.maxDepth ?? 3`.

**Spawn.** Children are started in their own process group — `src/llm.ts:563` sets detached on every non-Windows platform. That is why a killed parent block does not take its children with it.

**Model.** This is the one that surprises. An agent's `agent.yaml` model is applied by replacing only the provider and the model id over the ambient model config: `src/mcp/server.ts:487`. Anything else on that object, including an inherited sub-call model, survives from the ambient yaml. And the child process itself re-derives its config from scratch under the ordinary precedence documented at `src/cli.ts:35`, with the hardcoded fallback at `src/config.ts:122` when neither a settings file nor a yaml supplies one.

```
