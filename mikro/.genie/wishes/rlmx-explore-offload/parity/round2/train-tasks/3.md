## Question (authored for the training suite)

```text
How does this project read the NPU's power/clock state, and what exactly does it return when it cannot? I want the distinct unavailability reasons, not just 'it returns None'. Separately: iGPU telemetry discovery is a different mechanism in this codebase — what does it probe and how does it choose between candidates? Cite path:line for each claim.
```

## Reference answer (authored, and the source of the checklist)

```text
**The NPU read** is a debugfs read, rooted at the constant defined in `src/xdna_top/npu_power.py:30`, resolved per device before anything is opened.

It never raises, and it distinguishes three failures rather than collapsing them:

1. no accel directory at all — `src/xdna_top/npu_power.py:115`;
2. the directory exists but neither node could be read, which is the ordinary unprivileged case since debugfs is root-only — `src/xdna_top/npu_power.py:123`;
3. a node that read but carried nothing parsable — `src/xdna_top/npu_power.py:130`.

Only after none of those fires is the result marked available. Within a parsed line, the *active* DPM level is the bracketed token: the parser marks a state active on the bracket group at `src/xdna_top/npu_power.py:84`.

**iGPU discovery is unrelated** and lives in `src/xdna_top/discover_sysfs.py`. It starts pessimistic — the initial status at `src/xdna_top/discover_sysfs.py:18` is a CPU-only fallback, upgraded only when a busy-percent node is actually readable — and for power it walks hwmon and prefers the one whose name identifies the amdgpu driver, `src/xdna_top/discover_sysfs.py:55`, keeping the first readable candidate otherwise.

```
